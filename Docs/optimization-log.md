# 최적화 기록

원칙: 측정 → 수정 → 다시 측정. 모든 수치는 에디터가 아니라 Development Build에서 잰다.

## 측정 방법

- 도구: `Assets/Scripts/Diagnostics/PerfProbe.cs`. 개발 빌드와 에디터에서만 컴파일된다(`DEVELOPMENT_BUILD || UNITY_EDITOR`).
- `ProfilerRecorder`로 아래 4개를 GameScene에 있는 동안 매 프레임 모으고, 5초마다 평균을 `[PERF] window` 한 줄로 남긴다. 씬을 나갈 때는 `[PERF] total` 한 줄을 남긴다.

| 열 | 카운터 | 의미 |
| --- | --- | --- |
| `ui_ms` | `DBtJ.UIManager.Refresh` (`PerfMarkers.UIRefresh`) | 프레임당 UI 갱신 시간 |
| `gc_bytes` | `GC Allocated In Frame` | 프레임당 관리 힙 할당량 (전체) |
| `gc_count` | `GC Allocation In Frame Count` | 프레임당 할당 횟수 (전체) |
| `main_ms` | `Main Thread` | 메인 스레드 프레임 시간 (VSync 대기 포함이라 참고용) |

- 5초마다 찍는 로그 한 줄도 그 프레임에 할당을 만든다. 300프레임 이상에 나눠지므로 평균에 주는 영향은 작다.
- 실행: 빌드 두 개를 같은 PC에서 띄우고 로그 파일을 따로 지정한다.
  - `DBtJ.exe -logFile host.log` (방 만들기)
  - `DBtJ.exe -logFile guest.log` (참가)

### 측정 시나리오

1. 두 클라이언트로 GameScene에 들어간다.
2. 드로우 단계에서 아무것도 누르지 않고 30초 기다린다. 이 구간이 "가만히 있을 때 UI가 매 프레임 쓰는 비용"이다.
3. 히트와 스탠드로 한 라운드를 끝까지 진행한다(에이스 선택, 베팅 포함).
4. 다음 라운드 드로우 단계에서 다시 30초 기다린 뒤 종료한다.

## 2단계: 3D 테이블 (CardView 풀, 아틀라스 머티리얼 하나, TableView 이벤트)

측정일 2026-10-31. 같은 PC. 드로우 콜과 풀은 에디터 플레이 모드에서 같은 장면을 재현해 쟀다(드로우 콜 수는 에디터와 빌드가 같다). GC는 빌드 대전 로그에서 가져왔다.

### 렌더링: 드로우 콜과 SetPass (Frame Debugger)

장면: 내 카드 5장, 상대 카드 5장(마지막 1장 뒷면), 공유 카드 1장, 테이블, 덱, 벨, 2D HUD.

| 카드 렌더링 방식 | 3D 불투명 패스 | 전체 드로우 콜 | SetPass |
| --- | --- | --- | --- |
| **채택: 머티리얼 하나 공유 + 카드별 메시 UV** | `DrawSRPBatcher` 1개 이벤트 | 35 | **8** |
| 비교 A: 카드마다 MaterialPropertyBlock으로 UV 지정 | 카드 11장이 각각 `RenderLoop.Draw` + SRP 배치 1개 | 35 | **19** |
| 비교 B: 카드마다 머티리얼 인스턴스 | `DrawSRPBatcher` 1개 이벤트 | 35 | 8 |

읽는 법:
- 카드 11장, 테이블, 덱, 벨이 SRP Batcher로 한 번에 그려진다. 같은 장면에서 MaterialPropertyBlock 방식은 카드 수만큼 SRP Batcher에서 빠져 SetPass가 8 → 19로 늘었다. 카드가 늘면 같이 늘어난다.
- URP의 SRP Batcher는 머티리얼이 아니라 셰이더 단위로 묶기 때문에, 카드마다 머티리얼 인스턴스를 만들어도(B) 배칭은 깨지지 않는다. B의 비용은 GPU가 아니라 카드마다 Material 객체가 생기는 메모리와 생성 비용이다. 그래서 채택 방식의 실제 이득은 "MPB를 쓰지 않아 SRP Batcher를 유지"하고 "머티리얼을 카드 수만큼 만들지 않는 것"이다.
- 전체 35 중 16은 2D HUD Canvas다. 3단계에서 HUD를 줄이거나 정적/동적 Canvas로 나누는 것이 다음 대상이다.

### TableView 처리 시간 (에디터, 참고값)

시뮬레이션 200라운드(라운드당 이벤트 12개: 라운드 시작, 카드 10장, 공개)를 TableView 구독 상태와 해제 상태로 돌린 시간 차이: **라운드당 약 0.18ms, 이벤트당 약 0.015ms**. 에디터 값이라 빌드보다 느리다. 빌드 값은 PerfProbe의 `table_ms` 열(이번에 추가)로 다음 대전부터 기록된다.

에디터에서 호출 단위 할당량을 재려 했지만 `GC.GetAllocatedBytesForCurrentThread`, `GC.GetTotalMemory`, `Profiler.GetMonoUsedSizeLong` 모두 TableView 없이 돌린 기준조차 0으로 나와 신뢰할 수 없어서 기록하지 않았다. 할당은 위의 빌드 프레임 단위 수치로 판단한다.

## 3단계: 정보를 물건으로 (칩 인스턴싱, 아이템 오브젝트, HUD 축소)

측정일 2026-10-31. 렌더링은 에디터 플레이 모드에서 같은 장면을 재현해 Frame Debugger로, GC와 시간은 빌드 대전 로그로 쟀다.

장면: 베팅 단계, 내 카드 5장과 상대 카드 5장, 공유 카드, 칩 5더미(내 36, 상대 33, 내 베팅 1, 상대 베팅 4, 팟 11 → 화면의 칩 18개), 내 아이템 3개와 상대 아이템 2개, 더미 숫자 5개.

### Canvas (HUD)

| 항목 | 2단계 | 3단계 |
| --- | --- | --- |
| HUD Canvas 그리기 이벤트 | 16 | **8** |
| Raycast Target | 상호작용 없는 그래픽 45개에 켜져 있음 | **45개 끔**. 버튼과 모달 패널 배경 25개만 남김 |

칩, 베팅, 팟, 아이템 슬롯 패널을 끄고 테이블 물건으로 옮겼다. 자주 바뀌는 글자(합계, 단계 안내, 아이템 알림)는 중첩 Canvas `DynamicHud`로 분리해서, 이 글자가 바뀔 때 나머지 HUD는 다시 만들지 않는다.

### 칩: RenderMeshInstanced와 GameObject 비교

| 칩 18개를 그리는 방식 | 전체 드로우 콜 | SetPass | 칩 GameObject |
| --- | --- | --- | --- |
| **채택: `Graphics.RenderMeshInstanced` (액면가마다 1번)** | **63** | 15 | 0 |
| 비교: 칩마다 GameObject + MeshRenderer | 93 | **11** | 18 |

읽는 법:
- 인스턴싱은 칩 그리기를 불투명 3번, 그림자 3번으로 묶어 드로우 콜을 30개 줄였다(−32%). 칩이 늘어날수록(최대 약 30개) 차이가 커진다.
- 대신 SetPass가 4개 늘었다. GameObject 칩은 SRP Batcher가 이미 싸게 묶고 있어서, 인스턴싱 호출은 그 묶음 밖에서 따로 상태를 잡기 때문이다. URP에서는 SRP Batcher가 이미 강해서 인스턴싱의 이득이 Built-in 파이프라인만큼 크지 않다.
- 그래도 채택한 이유: 칩 GameObject가 0개라 날아가는 연출 중에도 Transform 갱신과 오브젝트 생성이 없고, 행렬 배열을 미리 만들어 두어 프레임당 할당이 없다.

### 전체 드로우 콜이 35 → 63으로 늘어난 이유

3단계에서 테이블 위 물건이 늘었다. 아이템 오브젝트는 여러 부품으로 되어 있고(돋보기 3, 플래시 3, 봉투 2), 칩과 그림자가 추가되고, 더미 숫자 5개가 생겼다. 더미 숫자는 TextMeshPro 셰이더라 투명 패스에서 하나씩 따로 그려진다(5개). 다음 대상은 다음 두 가지다.
- 아이템 부품을 메시 하나로 합치기. 4단계 Meshy 모델로 교체하면 자연히 줄어든다.
- 숫자 라벨을 줄이거나 하나의 메시로 합치기.

## 4단계 준비: 텍스처 압축 (카드 시트)

| --- | --- | --- | --- |
| 원래 (최대 2048) | 2048×1050 | **RGBA32 (무압축)** | 8.2 MB |
| 시도: 4096 + BC7 + 밉맵 | 2496×1280 | **RGBA32 (무압축)** | 16.3 MB |
| **채택: 4096 + BC7, 밉맵 끔** | 2496×1280 (원본) | **BC7** | **3.1 MB** |

원인 두 가지를 실험으로 확인했다(같은 PNG를 설정만 바꿔 다시 들여옴).
- 원본 2496×1280이 최대 크기 2048에 맞춰 2048×1050으로 줄면서 높이가 4의 배수가 아니게 됐다. BC/DXT는 4×4 블록 단위라 Unity가 압축을 포기하고 원본 그대로 넣었다.
- 2의 거듭제곱이 아닌(NPOT) 텍스처에 밉맵을 켜면 크기가 4의 배수여도 압축되지 않는다(2496×1280 + 밉맵 → RGBA32). 스프라이트 타입은 NPOT를 POT로 자동 늘리는 옵션도 쓸 수 없다.

결과: 카드 시트 8.2 MB → 3.1 MB(−62%), 해상도는 오히려 원본으로 올라갔다. 빌드의 텍스처 합계 24.1 MB → 19.0 MB, 빌드 전체 187.3 MB → 182.2 MB.

남은 개선 후보: 카드를 2048×1024 같은 POT 아틀라스로 다시 배치하면 BC7에 밉맵까지 켤 수 있다(약 2.8 MB). 지금은 밉맵이 없어 멀리 있는 카드가 약간 거칠게 보일 수 있다.

### 그 밖에 빌드에 들어가 있는 것
- 빌드 씬 목록에 Photon 데모 씬 `FusionIntroShared`가 남아 있어 데모 텍스처(`DemoGroundTexture` 1 MB 등)가 같이 들어간다. 최적화 측정일에 빼고 전후를 기록한다.
- 칩 텍스처 `ChipPattern.png`는 256 DXT1에 밉맵 포함 42.8 KB. 액면가 3종이 같은 텍스처를 쓰고 색만 다르다.

## 4단계: Meshy 에셋 들여오기 (첫 시험: 벨)

측정일 2026-10-31. 도구: `Assets/Editor/MeshyAssetProcessor.cs` (UnityMeshSimplifier 3.1.1, MIT).

| 항목 | Meshy 원본 | 처리 후 |
| --- | --- | --- |
| 삼각형 | 313,410 | **2,000 (−99.4%)** |
| 기본 색 텍스처 | 2048×2048 JPG, 스프라이트 타입으로 들어옴 | **512×512 DXT1 + 밉맵** (약 170 KB) |
| 파일 | FBX 13.8 MB (텍스처 포함) | 메시 에셋 105 KB |
| 머티리얼 | FBX 기본 머티리얼 | URP Lit 1개 (기본 색 맵, 매끄러움 0.45) |

메모:
- Meshy 텍스트→3D 결과는 PBR 맵 없이 기본 색 텍스처 1장만 있었다. 계획했던 거칠기→매끄러움 변환은 필요 없었다.
- UV 경계를 보존하는 옵션을 켜면 감소가 25,436에서 멈췄다. Meshy UV는 조각이 많아 경계가 많기 때문이다. 보존을 끄고 2,000까지 줄였고, 플레이어 카메라 거리에서 텍스처 번짐이나 각진 면이 보이지 않는 것을 화면으로 확인했다.
- 텍스처를 2048 그대로 두었다면 DXT1 + 밉맵으로 약 2.7 MB다. 512로 줄여 약 94% 절약했다.

### 정정: Unity 안 폴리곤 감소는 품질 때문에 쓰지 않기로 함
위의 2,000 삼각형 결과는 개발자가 "너무 조잡하다"고 판정했다. 원본과 나란히 비교한 결과:
- Meshy 원본(313k)은 깔끔하다. 8k부터 받침이 울퉁불퉁해지고 돔 가장자리가 거칠어졌다.
- UV 경계를 보존하면 25,436에서 멈춘다. 2k보다 낫지만 울퉁불퉁함이 남는다.
- 2k 감소 후 노멀을 다시 계산하면 음영은 부드러워지지만 모양은 그대로 울퉁불퉁하다.

결론: quadric 감소는 Meshy의 조밀한 메시를 크게 줄이면 모양과 텍스처를 함께 망가뜨린다. 모양을 새로 짜고 텍스처를 다시 굽는 Meshy Remesh(웹)로 줄이고, Unity 도구는 텍스처, 머티리얼, 크기 처리만 맡는다. 감소 전후 수치는 Remesh 결과로 다시 기록한다.

### 정정 2: 텍스처가 찌그러져 보인 진짜 원인
Meshy FBX 10종의 텍스처 파일 이름이 모두 `Image_0.jpg`였다. Unity가 FBX 머티리얼의 텍스처를 이름으로 찾다 보니 10종 모두 `Ashtray_Textures/Image_0.jpg`(재떨이 텍스처)에 연결됐다. UV가 다른 모델의 텍스처를 읽으니 조각조각 엇갈린 무늬가 됐다. Meshy UV나 압축 탓으로 본 앞의 판단은 틀렸다.
- 확인: 같은 벨 메시에 자기 텍스처로 새 머티리얼을 만들면 깔끔하다. FBX 머티리얼로는 무늬가 엇갈린다.
- 대응: FBX 내장 머티리얼은 쓰지 않는다. `MeshyAssetProcessor`가 FBX마다 자기 텍스처를 꺼내 URP Lit 머티리얼을 새로 만든다.
