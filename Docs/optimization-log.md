# 최적화 기록

원칙: 측정 → 수정 → 다시 측정. 모든 수치는 에디터가 아니라 Development Build에서 잰다.

## 측정 방법

- 도구: `Assets/Scripts/Diagnostics/PerfProbe.cs`. 개발 빌드와 에디터에서만 컴파일된다(`DEVELOPMENT_BUILD || UNITY_EDITOR`).
- `ProfilerRecorder`로 아래 4개를 GameScene에 있는 동안 매 프레임 모으고, 5초마다 평균을 `[PERF] window` 한 줄로 남긴다. 씬을 나갈 때는 `[PERF] total` 한 줄을 남긴다.

| 열 | 카운터 | 의미 |
| --- | --- | --- |
| `ui_ms` | `DBtJ.UIManager.Refresh` (`PerfMarkers.UIRefresh`) | 프레임당 UI 갱신 시간 |
| `gc_bytes` | `GC Allocated In Frame` | 프레임당 관리 힙 할당량 (전체) |
| `gc_count` | `GC Allocation In Frame Count` | 프레임당 할당 횟수 (전체) |
| `main_ms` | `Main Thread` | 메인 스레드 프레임 시간 (VSync 대기 포함이라 참고용) |

- 5초마다 찍는 로그 한 줄도 그 프레임에 할당을 만든다. 300프레임 이상에 나눠지므로 평균에 주는 영향은 작다.
- 실행: 빌드 두 개를 같은 PC에서 띄우고 로그 파일을 따로 지정한다.
  - `DBtJ.exe -logFile host.log` (방 만들기)
  - `DBtJ.exe -logFile guest.log` (참가)

### 측정 시나리오

1. 두 클라이언트로 GameScene에 들어간다.
2. 드로우 단계에서 아무것도 누르지 않고 30초 기다린다. 이 구간이 "가만히 있을 때 UI가 매 프레임 쓰는 비용"이다.
3. 히트와 스탠드로 한 라운드를 끝까지 진행한다(에이스 선택, 베팅 포함).
4. 다음 라운드 드로우 단계에서 다시 30초 기다린 뒤 종료한다.

## 1단계: UIManager 폴링 → 이벤트 기반 갱신

### 전 (기준, 커밋 c2200ac + 측정 코드)

- 측정일 2026-10-30. 노트북 RTX 5050 Laptop, 16스레드. Development Build, 1280×720 창 모드, 두 클라이언트 같은 PC.
- 시나리오를 다 지키지 못함: 30초 대기 없이 약 20초 동안 세 라운드를 진행하고 종료. 구간 평균은 5초 창마다 여러 단계가 섞여 있다. `phase`는 창이 끝난 시점의 단계다.
- 첫 창(frames=1)은 측정기 타이머가 로비에서 이미 지나 있어서 생긴 값이라 표에서 뺐다.

- gc 열은 게임 전체 값이라 UI 외(Fusion 등)도 섞여 있다.

### 전후 비교 (전체 평균)

| 역할 | 지표 | 전 | 후 | 변화 |
| --- | --- | --- | --- | --- |
| 호스트 | ui_ms | 0.0274 | 0.0029 | **−89%** |
| 호스트 | gc_bytes | 325.8 | 159.1 | **−51%** |
| 호스트 | gc_count | 7.41 | 2.00 | **−73%** |
| 게스트 | ui_ms | 0.0269 | 0.0028 | **−90%** |
| 게스트 | gc_bytes | 239.5 | 104.7 | **−56%** |
| 게스트 | gc_count | 6.91 | 1.80 | **−74%** |

읽는 법:
- UI 비용이 "매 프레임"에서 "상태가 바뀔 때만"으로 바뀌었다. 조용한 구간(창 2~4)은 프레임당 0.0003~0.0009ms까지 떨어진다. 창 1이 높은 것은 게임 시작 직후 카드 프리팹 생성 같은 첫 갱신이 몰려 있어서다.
- 프레임당 할당 횟수가 약 7회에서 약 2회로 줄었다. 줄어든 약 5회는 매 프레임 `Refresh`가 만들던 문자열이 맞다는 근거다(칩, 팟, 베팅 숫자 5개). 남은 약 1.5~2회는 UI 밖(Fusion 등)이다. 다음 측정 대상으로 남긴다.
- main_ms는 거의 그대로다(약 5.0~5.2ms). UI가 프레임에서 차지하던 비중이 원래 작았기 때문이다. 이 항목의 효과는 프레임 시간이 아니라 **할당 감소와 "아무 일 없을 때 일하지 않는 구조"**로 설명한다.

## 2단계: 3D 테이블 (CardView 풀, 아틀라스 머티리얼 하나, TableView 이벤트)

측정일 2026-10-31. 같은 PC. 드로우 콜과 풀은 에디터 플레이 모드에서 같은 장면을 재현해 쟀다(드로우 콜 수는 에디터와 빌드가 같다). GC는 빌드 대전 로그에서 가져왔다.

### 렌더링: 드로우 콜과 SetPass (Frame Debugger)

장면: 내 카드 5장, 상대 카드 5장(마지막 1장 뒷면), 공유 카드 1장, 테이블, 덱, 벨, 2D HUD.

| 카드 렌더링 방식 | 3D 불투명 패스 | 전체 드로우 콜 | SetPass |
| --- | --- | --- | --- |
| **채택: 머티리얼 하나 공유 + 카드별 메시 UV** | `DrawSRPBatcher` 1개 이벤트 | 35 | **8** |
| 비교 A: 카드마다 MaterialPropertyBlock으로 UV 지정 | 카드 11장이 각각 `RenderLoop.Draw` + SRP 배치 1개 | 35 | **19** |
| 비교 B: 카드마다 머티리얼 인스턴스 | `DrawSRPBatcher` 1개 이벤트 | 35 | 8 |

읽는 법:
- 카드 11장, 테이블, 덱, 벨이 SRP Batcher로 한 번에 그려진다. 같은 장면에서 MaterialPropertyBlock 방식은 카드 수만큼 SRP Batcher에서 빠져 SetPass가 8 → 19로 늘었다. 카드가 늘면 같이 늘어난다.
- URP의 SRP Batcher는 머티리얼이 아니라 셰이더 단위로 묶기 때문에, 카드마다 머티리얼 인스턴스를 만들어도(B) 배칭은 깨지지 않는다. B의 비용은 GPU가 아니라 카드마다 Material 객체가 생기는 메모리와 생성 비용이다. 그래서 채택 방식의 실제 이득은 "MPB를 쓰지 않아 SRP Batcher를 유지"하고 "머티리얼을 카드 수만큼 만들지 않는 것"이다.
- 전체 35 중 16은 2D HUD Canvas다. 3단계에서 HUD를 줄이거나 정적/동적 Canvas로 나누는 것이 다음 대상이다.

### 메모리: CardView 풀

| 항목 | 값 |
| --- | --- |
| 미리 만든 카드 | 24장 |
| 시뮬레이션 약 1,000라운드(카드 배치 약 11,000번) 후 풀이 만든 카드 | **24장 (추가 생성 0)** |
| 실제 대전 약 65초(13,000프레임) 중 풀 초과 경고 | 0회 |

2D에서는 `RenderCardRow`가 카드 수가 바뀔 때마다 Instantiate/Destroy를 했다. 3D에서는 게임 중 카드 오브젝트 생성과 파괴가 없다.

### 스크립트: 프레임당 GC (빌드 대전 로그)

| 단계 | 호스트 gc_bytes / gc_count | 게스트 gc_bytes / gc_count |
| --- | --- | --- |
| 기준 (2D, 폴링) | 325.8 / 7.41 | 239.5 / 6.91 |
| 1단계 (2D, 이벤트) | 159.1 / 2.00 | 104.7 / 1.80 |
| **2단계 (3D 테이블)** | **102.5 / 1.84** | **104.4 / 1.68** |

3D 테이블, 카드 연출, 레이캐스트 입력, 카메라가 추가됐지만 프레임당 할당은 늘지 않았다. 2단계 세션이 약 65초로 1단계(약 25초)보다 길고 대기 구간이 많아 평균이 낮게 나온 부분도 있다.

### TableView 처리 시간 (에디터, 참고값)

시뮬레이션 200라운드(라운드당 이벤트 12개: 라운드 시작, 카드 10장, 공개)를 TableView 구독 상태와 해제 상태로 돌린 시간 차이: **라운드당 약 0.18ms, 이벤트당 약 0.015ms**. 에디터 값이라 빌드보다 느리다. 빌드 값은 PerfProbe의 `table_ms` 열(이번에 추가)로 다음 대전부터 기록된다.

에디터에서 호출 단위 할당량을 재려 했지만 `GC.GetAllocatedBytesForCurrentThread`, `GC.GetTotalMemory`, `Profiler.GetMonoUsedSizeLong` 모두 TableView 없이 돌린 기준조차 0으로 나와 신뢰할 수 없어서 기록하지 않았다. 할당은 위의 빌드 프레임 단위 수치로 판단한다.
